## เป้าหมาย

ยกระดับหน้าเว็บจากต้นแบบให้เป็นเครื่องมือที่คนเชียงใหม่ใช้ตัดสินใจได้จริงในฤดูน้ำหลาก โดยเน้นการใช้งานมากกว่าความสวย

ผู้ใช้หลักคือคนที่อยู่หรือทำงานริมแม่น้ำปิง (ร้านค้าย่านวัดเกต ช้างคลาน ป่าพร้าวนอก ฯลฯ) เปิดดูจากมือถือ ส่วนใหญ่ตอนกังวลว่าน้ำจะขึ้น
ผู้ใช้รองคือนักวิจัยและเจ้าหน้าที่ที่อยากดูข้อมูลเชิงลึก

หน้าแรกต้องตอบคำถามเหล่านี้ได้ภายใน 5 วินาทีโดยไม่ต้องเลื่อน
1. ตอนนี้น้ำอยู่ระดับไหน อันตรายไหม
2. อีกไม่กี่ชั่วโมงจะขึ้นหรือลง ถึงระดับไหน
3. ฉันต้องทำอะไรไหม
4. ข้อมูลนี้สดแค่ไหน เชื่อได้แค่ไหน

## ฟีเจอร์ที่ต้องการ เรียงตามความสำคัญ

### P0 — ต้องมี

1. **สิ่งที่ควรทำตามสถานะ** แต่ละระดับ (ปกติ/เฝ้าระวัง/วิกฤต/ล้นตลิ่ง) มีคำแนะนำสั้น 2–3 ข้อ เก็บข้อความไว้ในไฟล์ config ที่แก้ได้โดยไม่ต้องแตะโค้ด คำแนะนำต้องเป็นแนวปฏิบัติทั่วไป เช่น ยกของขึ้นที่สูง หรือติดตามประกาศจังหวัด ห้ามแต่งข้อมูลเฉพาะพื้นที่
2. **เวลาที่คาดว่าจะถึงเกณฑ์ถัดไป** เมื่อพยากรณ์ 6 ชม. ข้ามเกณฑ์ ให้แสดงเป็นช่วงเวลา เช่น "อาจถึง 3.70 ม. ราว 13:00–15:00 น." จากค่าพยากรณ์และช่วงความไม่แน่นอน ถ้าไม่ข้ามเกณฑ์ไม่ต้องแสดง และห้ามประมาณเกิน 6 ชม.
3. **ระดับน้ำของฉัน** ผู้ใช้ตั้งได้ว่า "น้ำเข้าบ้าน/ร้านฉันที่ X ม. ตามไม้วัด P.1" เก็บใน localStorage แสดงเป็นเส้นบนไม้วัดและกราฟ และแจ้งในหน้าเมื่อพยากรณ์เข้าใกล้ ต้องมีคำอธิบายสั้น ๆ ว่าหาตัวเลขนี้อย่างไร (เทียบกับปี 2567 ที่ยอด 5.30 ม.)
4. **ความสดของข้อมูล** แสดงชัดว่าวัดเมื่อกี่นาทีที่แล้ว ถ้าเกิน 2 ชม. เปลี่ยนสถานะเป็นเตือน และอธิบายว่ากรมชลฯ ป้อนข้อมูลช้า 1–2 ชม. เป็นเรื่องปกติ ถ้ารีเฟรชอัตโนมัติแล้วยังได้ข้อมูลเดิม ห้ามทำให้ดูเหมือนมีค่าใหม่
5. **กราฟที่ใช้งานได้จริง**
   - เลือกช่วงได้ 24 ชม. / 3 วัน / 7 วัน / 30 วัน
   - แตะหรือ hover แล้วเห็นเวลาและค่า
   - แสดงเส้นเกณฑ์และระดับน้ำของฉัน
   - เปิด/ปิดเส้นเทียบ "น้ำท่วม 2567 ณ ช่วงเวลาเดียวกันของเหตุการณ์" ได้ (ใช้ data/seed)
6. **ผังแม่น้ำต้นน้ำ** แผนภาพแบบเส้นตรง (schematic ไม่ใช่แผนที่) เรียง P.20 → P.75/P.92 → P.67 → P.21 → P.1 แต่ละจุดแสดงระดับเทียบตลิ่ง ลูกศรขึ้น/ลง 3 ชม. และเวลาเดินทางถึงตัวเมือง (ใส่เฉพาะค่าที่มีแหล่งอ้างอิง) ฝั่ง backend ต้องเพิ่ม P.75, P.92, P.20 โดยหา ThaiWater id จาก payload จริง ห้ามเดา id ถ้าหาไม่ได้ให้หยุดถามผม
7. **โหมดความแม่นต่ำ** ถ้าระดับน้ำปัจจุบันอยู่นอกช่วงข้อมูลเทรน หรือข้อมูลต้นน้ำไม่ครบ ให้แสดงข้อความในหน้าว่าตัวเลขพยากรณ์เชื่อถือได้น้อยลงเพราะอะไร (backend ต้องส่ง flag นี้มาใน API)
8. **ระดับน้ำเปลี่ยนโดยปริมาณน้ำไม่เปลี่ยน** เมื่อ API ส่ง `level_controlled.detected` ให้แสดงข้อความสั้น ๆ ข้างตัวเลขว่า ระดับที่เปลี่ยนช่วงนี้อาจเกิดจากการบริหารจัดการน้ำ ไม่ใช่น้ำที่ไหลมามากขึ้นหรือน้อยลง และตัวเลขพยากรณ์อาจคลาดเคลื่อนมากกว่าปกติ ห้ามบอกว่าเป็นการเปิด/ปิดประตูน้ำ
9. **แนวโน้ม 12 ชม. ที่ถูกซ่อน** เมื่อ `trend12` เป็น null ให้แสดงเหตุผลจาก `trend12_hidden_reason` เป็นภาษาคนทั่วไปแบบสั้น ๆ หรือไม่แสดงอะไรเลย ห้ามแสดงว่า "ทรงตัว" แทน

### P1 — ควรมี

10. **ฝน** แสดงฝนสะสม 24 ชม. ที่ผ่านมาในลุ่มน้ำตอนบน (ThaiWater `rain_24h`) และพยากรณ์ฝน 12 ชม. (Open-Meteo) เป็น context เท่านั้น ยังไม่ใส่ในโมเดล
11. **หน้าความแม่นย้อนหลัง** ใช้ตาราง `forecast_log` จากงานก่อนหน้า แสดง error 7/30 วันล่าสุดแยกตาม horizon, coverage ของช่วงความไม่แน่นอน และกราฟพยากรณ์เทียบจริง เพื่อให้ผู้ใช้เห็นว่าโมเดลแม่นแค่ไหนในสภาพจริง
12. **PWA** ติดตั้งลงหน้าจอได้ เปิดออฟไลน์แล้วเห็นข้อมูลล่าสุดที่เคยโหลด พร้อมบอกว่าเป็นข้อมูลเก่า
13. **แชร์** ปุ่มแชร์ (Web Share API และ fallback คัดลอกลิงก์) และ Open Graph image ที่แสดงระดับน้ำและสถานะปัจจุบัน สำหรับแชร์ใน LINE หรือ Facebook
14. **ภาษาไทย/อังกฤษ** สลับได้ เก็บข้อความทั้งหมดในไฟล์แปลไฟล์เดียว
15. **ธีมมืด** ตามระบบ ใช้ CSS variables ชุดเดิม

### P2 — ทำเมื่อ P0–P1 เสร็จ (เสนอแผนก่อน ยังไม่ต้องทำ)

16. การแจ้งเตือน: Web Push และ/หรือ Telegram bot เมื่อพยากรณ์ข้ามเกณฑ์หรือระดับน้ำของผู้ใช้ (LINE Notify ปิดบริการไปแล้ว ถ้าจะใช้ LINE ต้องใช้ Messaging API)
17. หน้าข้อมูลสำหรับนักวิจัย: ดาวน์โหลด CSV รายชั่วโมงทุกสถานี และ JSON API ที่มีเอกสาร
18. หน้า admin/health แสดงสถานะ poll, 429, backfill, การ retrain

## สิ่งที่ต้องรักษา

- เอกลักษณ์ไม้วัดระดับน้ำแดง-ขาว ตัวเลขใหญ่ โทนสี และฟอนต์เดิม ปรับให้ดีขึ้นได้แต่ห้ามเปลี่ยนทิศทาง
- กฎใน CLAUDE.md ทุกข้อ โดยเฉพาะ: 12 ชม. เป็นแนวโน้มเท่านั้น, ทุกพยากรณ์มีช่วงความไม่แน่นอน, ไม่แต่งข้อมูล, มีข้อความว่าไม่ใช่ระบบเตือนภัยทางการ
- โหมดสาธิตต้องใช้ได้กับทุกฟีเจอร์ (ข้อมูลที่โหมดสาธิตไม่มี เช่น ฝนปี 2567 ให้ซ่อนพร้อมบอกเหตุผล)
- มือถือ 360px ก่อน, ใช้ keyboard ได้, contrast ผ่าน WCAG AA, รองรับ prefers-reduced-motion
- หน้าแรกโหลดเร็วบน 4G: JS + CSS รวมไม่เกิน ~150 KB ไม่นับฟอนต์

## เรื่องเทคโนโลยี

ตอนนี้ frontend เป็น vanilla JS ไม่มี build step ถ้าคิดว่าฟีเจอร์ชุดนี้ควรใช้ build tool หรือ framework (เช่น Vite + Preact) ให้เสนอพร้อมเหตุผลและถามผมก่อน ห้ามเปลี่ยนเอง ฝั่ง backend ใช้ FastAPI + SQLite ต่อ
